给一段 dmesg / sosreport，自动比对已知内核问题、定位根因、给出修复建议，并让每一条结论都能回溯到真实 commit / CVE 的证据链。
产品介绍 · OLK（openEuler）6.6 / 5.10 · 离线优先

0这是什么 · 给谁用

一个离线优先的 Linux 内核故障诊断智能体。它不替代你的监控，而是在故障已经发生、你拿到一段崩溃日志之后，帮你快速回答：是不是已知内核 bug、根因在哪、怎么修，并区分“内核 bug”还是“配置 / 设计使然”。围绕“这是不是我的锅”的结构化故障定界正在交付中（见 §1）。

角色典型场景
OS SRE 值班收到 OOM / softlockup / panic 告警，要快速判定是内核 bug、配置问题，还是上层的锅
内核 / 后端工程师拿到崩溃栈，想知道是不是已知 bug、该看哪个 commit
OS 维护团队评估上游某 commit 是否需要 backport 到 OLK 内核

1解决 SRE 的三个真实痛点

① 故障定界 —— “这是不是我的锅” 部分已就绪 · 在建强化
报到 OS 团队的事件，60–80% 其实是应用 / 驱动 / 硬件的锅，但 SRE 大量时间花在自证清白、给下一棒整理证据。今天已能：区分“内核 bug”还是“配置 / 硬件 / 设计使然”（如 cgroup 触顶 OOM 判为非内核 bug）。在建：产出结构化定界结论 ——定界：[应用层] · 责任：[业务团队] · 置信度：0.85—— 并自动打包 handoff 取证材料。
② 已知问题秒级分诊 —— “是不是已知 bug / 要不要 backport”
拿到崩溃栈，自动比对内核 commit / CVE / syzbot 库，判定是否命中已知问题、是否已修复、能否 backport 到 OLK，省掉人工翻 lore.kernel.org 和 bugzilla 的几十分钟。
③ 未知问题加速 —— “没 SOP 的疑难杂症”
已知故障有 runbook，没 SOP 的问题单 case 平均 2–4 小时纯靠人脑 + 搜索引擎 + 内部 wiki。产品用知识图谱 + LLM 把“查什么、看哪里”的调研过程压缩到分钟级。

3项目整体规划：通用 Linux 故障诊断 agent 蓝图

我们的目标，从一开始就是一个通用的 Linux 故障诊断智能体。它本质上是通用智能体架构（Planner · Memory · Tools · Feedback · Perception）在内核诊断域的特化——Memory 落成内核知识图谱，Tools 落成内核取证工具集，Feedback 落成 ReAct + 自我批驳 + 证据校验：

为什么从知识图谱做起？一个诊断 agent 的上限，不在于接了多少工具，而在于有没有一个可信的证据底座去解释这些工具吐出的信号。vmcore、Prometheus 给你的是信号（谁挂了、内存什么水位）；但“是不是已知 bug、谁修的、是不是我的锅”这些意义，只能从内核 commit / CVE / 邮件 / syzbot 这张关系网里来。没有它，LLM 接再多工具，产出的也只是“措辞自信的幻觉”。所以我们先做知识图谱——因为我们首先需要证据。

4技术实现：先把证据底座做扎实（知识图谱）

图 2 里的 Memory（知识图谱）自身是一条完整的数据管线：六类公开数据源入库 PostgreSQL，由链接器织成关系网，再经七路检索喂给诊断 agent。

  • 数据底座：1.5M OLK commits + 115K LKML 邮件 + 16K CVE + 8K bug + 6.8K syzbot 报告，织成 commit ↔ bug ↔ CVE ↔ 邮件 ↔ 符号 ↔ Fixes ↔ revert 的关系网（约 26 万条边）。这是“判定责任、追溯修复”的根据所在。
  • 检索为什么不用向量：内核术语是精确 token（mem_cgroup_out_of_memory、CONFIG_MEMCG），BM25 + 图谱关系 + LLM 精排比通用 embedding 更准、更可解释 —— 命中能说清“因为哪个符号”，而不是一个模糊的相似度分数。
  • 诊断引擎（ReAct 智能体）：按资深工程师的反射逐层调研 —— 先问“我见过没”（同栈帧检索）→ 符号反查 → 跨源关键词检索 → 候选验证（读 diff、查 revert 链、查维护者）。走遍整条调用栈，而不是死锚栈顶那一帧。
  • 取证层（接入中）：把崩溃栈里的 func+0x4a/0x80 偏移解析到具体源码行，再 git blame 锁定改动它的 commit；提供 vmcore 时，用 drgn 只读分析锁持有 / OOM 上下文。

设计思路一图说清——确定性骨架夹一段 ReAct 自主调研：能复现的环节（分诊、绑定、报告）交给确定性流程，没 SOP 的调查环节交给受协议约束的 ReAct 循环：

三条可信度红线（SRE 最该关心的）：
 ① 不编 commit（设计原则 · 持续强化）—— 要求报告引用的每个 SHA 都来自本次调研工具的真实返回，而非凭模型记忆编造；端到端校验正在强化中；
 ② hardware-first —— 检测到 MCE / EDAC / 坏 DIMM 信号，直接跳出“内核 bug”路径，避免把硬件故障误诊成内核死锁；
 ③ 证据不足就明说 —— 没有足够证据时，显式输出“证据不足 + 还缺什么（vmcore / 完整 dmesg / 内核配置）”，而不是强行编一个像样的答案。

5当前适用边界

  • 专精 OLK（openEuler）6.6 + 5.10，暂不跨 Ubuntu / RHEL —— 跨 distro 后 70%+ 数据重复、收益不足 10%，单 distro 专精反而更准（在线扩展方向见 §3 蓝图）。
  • 当前为离线 KB 分析，不做 live debugging（不 SSH 到生产机执行命令）—— 接入实时可观测是 §3 蓝图里 Perception（在线感知）的规划方向。
  • 定位是诊断助手，不是 incident manager —— 给定界、根因和建议，不自动执行变更或 mitigate。

7端到端示例

下例基于评测用例 oom-001 构造，用于说明产出形态（示意）。

输入 · dmesg 片段
oom-kill:constraint=CONSTRAINT_MEMCG, oom_memcg=/app/java,
         task_memcg=/app/java, task=java, pid=1234
Out of memory: Killed process 1234 (java)
         anon-rss:3995200kB, oom_score_adj:0
memory: usage 4194304kB, limit 4194304kB, failcnt 47
输出 · 诊断报告
诊断结论：Form C · 非内核 bug —— cgroup 内存触顶，内核按设计正常工作

根因：OOM 由 CONSTRAINT_MEMCG 触发，usage(4194304kB) == limit(4194304kB) 且 failcnt 持续增长 —— 是 /app/java 这个 cgroup 触及自身内存上限，并非全局内存压力，也不是内核 bug。

修复建议（Form C · 非内核 bug）：

  • 排查 Java 进程内存（堆 3.8GB 已逼近 cgroup 4GB 上限）：检查 -Xmx 与容器 memory.max 是否匹配；
  • 如属正常负载增长，上调该业务的 memory.max 配额；无需 backport 任何内核 commit。

证据来源（每条可回溯）：dmesg 中 CONSTRAINT_MEMCG + usage==limit 信号 → 判定为 cgroup 限额场景，非全局 OOM。

即将补充 · 在建

在上述诊断之上自动产出 定界：[应用层] · 责任：[业务团队 / app-java]，并打包 handoff 取证材料（OS 层已排除证据 + 需要业务方反馈项），一键移交接手方。

对比价值：值班无需逐行读 dmesg、无需翻 commit 库，一眼看清“这是 cgroup 配置触顶、不是内核 bug”，并拿到可转交的证据。
